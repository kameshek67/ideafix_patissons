# Поступай по олимпиаде — БВИ и 100 баллов

Сервис для хакатона: двусторонний поиск льгот олимпиадников по данным
приёмных кампаний 2026 года (17 листов исходного XLSX).

* **Сценарий 1 — «Ищу олимпиады под ВУЗ»**: выбрал вуз → направление → видишь, какие олимпиады
  дают БВИ, какие — 100 баллов, и что нужно подтвердить ЕГЭ.
* **Сценарий 2 — «Куда поступить с моей олимпиадой»**: ввёл «Высшая проба» / «ВсОШ» / «пвг» →
  выбрал профиль олимпиады → получил **список вузов** → нажал на вуз → таблица его льгот.

Вся конкретика выводится **таблицами** (сортировка по колонке, фильтр по строке, выгрузка CSV).
Текстом остаются только общие правила вуза, в которых нет названий олимпиад, — они собраны
в свёрнутый блок «Общие правила и примечания».

```
Python 3.13 · uv · FastAPI · SQLAlchemy + Alembic · PostgreSQL · Redis · Dramatiq + RabbitMQ
Next.js 16 · React 19 · TanStack Query · клиент из OpenAPI · Tailwind 3 · Docker Compose
```

## Быстрый старт (Docker)

Нужен запущенный Docker Desktop (или демон docker на Linux). Из каталога проекта:

```bash
docker compose up --build -d
```

* сайт — http://localhost:8080
* API и Swagger — http://localhost:8000/docs

При первом старте сервис `migrate` применяет миграции и собирает базу из
`data/Olimpiady_BVI_100ballov.xlsx` (около минуты, видно в `docker compose logs -f migrate`).
База живёт в томе `pgdata` и переживает пересоздание контейнеров, поэтому дальше всё стартует
за секунды. Если порты 8000/8080 заняты (например, прежним прототипом — контейнеры `bvi-*`),
остановите его (`docker stop bvi-frontend bvi-backend`) или поднимите стек на других портах:

```bash
OLYMP_WEB_PORT=18080 OLYMP_API_PORT=18000 docker compose up --build -d
# PowerShell: $env:OLYMP_WEB_PORT=18080; $env:OLYMP_API_PORT=18000; docker compose up --build -d
```

Управление:

```bash
docker compose ps                         # статус контейнеров
docker compose logs -f api                # логи API
docker compose stop / start               # остановить / запустить
docker compose down                       # удалить контейнеры (база в томе остаётся)
docker compose down -v                    # удалить и базу — соберётся заново при следующем старте
docker compose run --rm migrate olymp-ingest                                # пересобрать базу из XLSX
docker compose exec worker python -m olymp_workers.tasks refresh-sources   # обновить ссылки вузов
```

## Разработка

Нужны [uv](https://docs.astral.sh/uv/), Node.js 22+, Docker и (по желанию) [just](https://just.systems).
PostgreSQL, Redis и RabbitMQ работают в контейнерах, API и сайт — с хоста, с перезагрузкой при правках.

```bash
cp .env.example .env
uv sync --all-packages && npm install
just up          # PostgreSQL, Redis, RabbitMQ (infra/compose.yaml)
just seed        # миграции + сборка базы из XLSX
just api         # API на :8000 (Swagger — /docs)
just web         # сайт на :3000, /api/v1/* проксируется на API
```

Без just на Windows всё это делает один скрипт: `.\run_local.ps1` (`-Rebuild` — пересобрать
базу, `-ApiPort 8010` — если порт 8000 занят); на Linux/macOS — `./run_local.sh`.

Остальные команды — `just --list`: `just test`, `just lint`, `just validate`, `just worker`,
`just openapi` (после изменения эндпоинтов: контракт `docs/openapi.json` и типы клиента),
`just compare` (сверка с прототипом, см. ниже).

## Что делает сборка базы (`olymp-ingest`)

Сборка идёт одной транзакцией: таблицы с данными очищаются и наполняются заново, поэтому
API до коммита видит прежнюю версию данных.

1. **Лист «База»** (675 строк) → `universities` / `programs` / `benefits`
   (формулировка правила + примечание + ссылка на источник).
2. **13 подробных листов** → строки таблиц (`layer='detailed'`), у каждого листа свой адаптер:

   | Лист | Что извлекается |
   |---|---|
   | ВШЭ подробно / филиалы / ВсОШ | программа × олимпиада × профиль × льгота, порог ЕГЭ, класс |
   | РЭУ подробно | 27 510 строк агрегируются в 8 124 правила (годы и предметы ЕГЭ схлопнуты) |
   | МИФИ подробно | списки кодов направлений раскрываются построчно |
   | Бауманка подробно | 10 групп направлений; «БВИ только победителям» → призёрам отдельная запись на 100 баллов |
   | Финуниверситет | группы программ 1–8, уровни олимпиад по годам |
   | КФУ подробно | и «все направления с ВИ по предмету», и явные списки кодов |
   | УрФУ подробно + легенда | коды профилей РСОШ расшифровываются по листу-легенде |
   | ЦУ фаст-трек, Иннополис, Пирогова, УрФУ +4 балла | фаст-трек, особые права, ИД |
   | ВШЭ международные | 12 международных олимпиад → БВИ членам сборных РФ |

3. **Справочник олимпиад.** В исходнике ~450 вариантов написания одного и того же
   (артефакты извлечения из PDF: `Всероссийская о4л импиада`, обрывки строк). Они схлопываются
   в **173 канонические олимпиады**: `squash()` строит ключ из одних букв, якоря из
   `olympiad_seeds.py` с исключениями отделяют, например, «Высшую пробу» от ВсОШ, обрывки
   приклеиваются к полному названию, плюс пользовательские сокращения: `всош`, `оммо`, `пвг`,
   `мош`, `нто`, `вышка`, `мфти`.
4. **Профили олимпиад** (`olympiad_profiles`, 635 шт.). Льгота даётся за пару «олимпиада + профиль»:
   у НТО это 49 профилей, у «Высшей пробы» — 34. Названия нормализуются, обрывки строк из PDF
   приклеиваются к полному профилю по вхождению подстроки или длинному общему началу.
5. **Разбор текстовых перечислений.** Сводные формулировки «Базы» вида
   `[143 вар.] «Высшая проба» (информатика, I ур.); «Ломоносов» (математика, I ур.); …`
   раскладываются в такие же строки таблиц (+913 строк). `parse_enumeration()` понимает четыре
   формата источников; названия проверяются по справочнику олимпиад. 859 исходных текстов
   скрыты как дубли разобранных таблиц (`layer='raw'`), 477 общих правил без названий олимпиад
   остались текстом (`layer='summary'`) и показываются примечаниями.
6. **Правила «по профилю олимпиады».** Часть вузов задаёт льготу профилем перечня:
   «любая олимпиада перечня I–III уровня по информатике и математике…». `parse_profile_rules()`
   вытаскивает профили, уровни и «кому», `ProfileIndex` сопоставляет их со справочником
   (со склонениями и сокращениями: ИКТ, ИИ, финтех…). Результат: **+23 720 строк**
   (`layer='derived'`, в интерфейсе — бейдж «по профилю»).
7. **Связи и индексы**: `benefit_olympiads` (59 098 связей «льгота ↔ олимпиада (+профиль)»),
   `benefit_keywords` (117 677 ключевых слов: уровень, победитель/призёр, класс, порог ЕГЭ,
   предметы) и полнотекстовый индекс `search_index` (tsvector, конфигурация `simple`).

Итог сборки: **39 вузов · 659 направлений · 48 963 строки таблиц (25 243 из документов +
23 720 выведенных из правил по профилю) + 477 текстовых правил · 173 олимпиады · 635 профилей**.

Результат детерминирован: порядок обхода строк задан явно, а итог совпадает со сборкой
прототипа на SQLite (ветка `main`) построчно — итоговые числа проверяет тест `apps/workers/tests`.

### Слои данных

| `layer` | что это | где видно |
|---|---|---|
| `detailed` | строка «олимпиада × профиль × уровень» из документа вуза | таблицы |
| `derived` | строка, выведенная из правила «любая олимпиада перечня с профилем X» | таблицы, бейдж «по профилю» |
| `summary` | правило вуза без названий олимпиад и профилей («уровень II — весь перечень») | блок примечаний |
| `raw` | исходное перечисление, уже разложенное в строки | только в БД, для трассировки |

### Как склеиваются «База» и подробные листы

Одно направление приходит из разных листов в разном виде: `№3. Прикладная математика и
информатика (01.03.02)` в «Базе» и `Прикладная математика и информатика` + код `01.03.02`
в «ВШЭ подробно». `ProgramRegistry` строит для программы несколько ключей (имя без кодов,
набор кодов, «Группа N», предмет ВИ в кавычках) и объединяет записи — поэтому в карточке
направления рядом лежат и сводное правило вуза, и подробный список олимпиад.

## API

Публичные эндпоинты — под `/v1` (сайт обращается к ним через прокси Next.js `/api/v1/*`).
Ошибки — в формате RFC 9457 (`application/problem+json`), ответы поиска кэшируются в Redis
(ключ включает время сборки базы), запросы с одного IP ограничены (600 в минуту). Адрес
посетителя сайта до API доносит `apps/web/src/proxy.ts` (заголовок `X-Forwarded-For`), а API в
Docker доверяет этому заголовку только от адресов внутренних сетей (`FORWARDED_ALLOW_IPS`).
Без обратного прокси (nginx, Caddy) перед сайтом клиент может подставить свой заголовок, поэтому
лимит защищает от случайной перегрузки, а не от целенаправленного обхода.

| Метод | Назначение |
|---|---|
| `GET /healthz`, `GET /readyz` | жив ли сервис / доступна ли собранная база |
| `GET /v1/stats` | счётчики для блока «О базе», статистика по вузам, топ олимпиад, отчёт сборки |
| `GET /v1/regions` | Москва / Санкт-Петербург / Регионы |
| `GET /v1/universities?region=&q=` | вузы с числом направлений и льгот |
| `GET /v1/programs?university_id=&q=` | направления вуза |
| `GET /v1/olympiads?q=&featured=&limit=` | автокомплит по названиям и сокращениям (+ число профилей) |
| `GET /v1/olympiads/{id}/profiles` | профили олимпиады со счётчиками БВИ / 100 баллов / вузов |
| `GET /v1/search/by-program?program_id=` | строки таблиц по типам льгот, примечания, олимпиады, источники |
| `GET /v1/search/by-olympiad?q=&olympiad_id=&profile_id=&university_id=&region=&benefit_type=` | обратный поиск: список вузов, а с `university_id` — все строки выбранного вуза |

```bash
curl "http://localhost:8000/v1/search/by-olympiad?q=высшая%20проба&region=Москва"
curl "http://localhost:8000/v1/olympiads?q=нто"
curl "http://localhost:8000/v1/search/by-program?program_id=135"
```

`by-olympiad` возвращает точные итоги (`total_universities`, `total_programs`) отдельным
агрегатом, а подробные строки — с лимитом, поэтому счётчики не «плывут» на больших олимпиадах.

### Сверка с прототипом

Ответы нового API совпадают с API прототипа из ветки `main`. Проверить можно скриптом —
он сравнивает все направления, все олимпиады с профилями и фильтрами, свободный ввод
и запасной полнотекстовый поиск, включая порядок элементов:

```bash
# прототип: docker compose up в ветке main (API на :8000)
just compare            # или: uv run python scripts/compare_with_prototype.py --quick
```

## Откуда берутся ссылки на документы

Прямая ссылка на PDF живёт один приёмный сезон (`…/2026/Lgoty.pdf`), а адрес раздела
«Документы / Олимпиады» у вуза меняется редко. Поэтому:

1. **[university_pages.py](apps/workers/src/olymp_workers/university_pages.py)** — единственный
   файл, который поддерживается руками: вуз → стабильная страница раздела. Статусы: `verified`,
   `page`, `guarded` (сайт закрыт от автоматических запросов), `todo`.
2. **`olymp-refresh-sources`** обходит эти страницы, находит на них файлы по ключевым словам
   («олимпиад», «особые права», «приложение», «правила приёма») и складывает их в таблицу
   `university_documents` и кэш `data/university_documents.json`:

   ```bash
   uv run olymp-refresh-sources            # обновить
   uv run olymp-refresh-sources --dry-run  # только посмотреть
   uv run olymp-refresh-sources --only кфу # один вуз
   uv run python -m olymp_workers.tasks refresh-sources   # то же фоновой задачей (воркер Dramatiq)
   ```

3. **Сборка базы** подхватывает кэш, поэтому обход сайтов нужен не после каждой пересборки,
   а раз в сезон. В карточке направления первой идёт кнопка «Документы приёмной комиссии»
   (страница), за ней — конкретные файлы, найденные на ней.

## Проверка качества данных

```bash
uv run olymp-validate                 # быстрые проверки по базе
uv run olymp-validate --check-links   # плюс HTTP-проверка всех ссылок на первоисточники
```

Что проверяется: направления без ссылки на источник, «ссылки», которые на самом деле текст,
URL с пробелами, доля строк без опознанной олимпиады, полностью одинаковые строки таблиц,
подозрительно редкие олимпиады, направления без таблиц, доля строк «по профилю», вузы без
страницы приёмной комиссии, страницы со статусом `todo` и ссылки старше полугода.
Код возврата 1, если есть ошибки уровня ERROR — годится для CI.

## Модель данных

```
universities(id, name, short_name, region, city, note, site_url, docs_url, docs_title, region_group)
programs(id, university_id, faculty_or_direction, profile_name, code, note,
         source_title, source_url, source_sheet, sort_order)
benefits(id, program_id, benefit_type, raw_conditions_text, layer,
         olympiad_profile, olympiad_subject, level, winner_role, grade,
         confirm_subject, min_ege, award_subject, years, note, source_title, source_url, source_sheet)
olympiads(id, canonical_name, short_name, squash_key, kind, is_featured, mentions, bvi_count, sto_count, uni_count)
olympiad_aliases(id, olympiad_id, alias, squash_alias, is_generic)
olympiad_profiles(id, olympiad_id, name, squash_key, level, mentions, bvi_count, sto_count, uni_count)
benefit_olympiads(id, benefit_id, olympiad_id, profile_id, profile, level, winner_role, matched_via)
benefit_keywords(id, benefit_id, kind, keyword)
university_documents(id, university_id, title, url, checked_at)
search_index(benefit_id, document tsvector)

```

Схема меняется только миграциями (`packages/db/src/olymp_db/migrations`). У всех текстовых
колонок сортировка `"C"` — строки упорядочиваются побайтно, как в прототипе.

`benefit_type`: `БВИ`, `100 баллов`, `Особое право (БВИ/100)` (Иннополис — конкретное право
определяют правила приёма), `Фаст-трек` (ЦУ), `ИД (доп. баллы)` (УрФУ).

## Тесты и CI

`just test` (или `uv run pytest` и `npm test --workspace olymp-web`). Тестам с базой нужен
PostgreSQL (`just up`): они собирают базу из настоящего XLSX во временной БД и сверяют итоги
с прототипом. CI (`.github/workflows/ci.yml`) прогоняет ruff, mypy, import-linter, pytest,
проверяет актуальность `docs/openapi.json` и типов клиента, тесты и сборку сайта.

## Известные ограничения

* Строки со слоем `derived` — это **вывод из правила вуза**, а не цитата из его таблицы:
  «любая олимпиада перечня с профилем X» разворачивается по справочнику профилей, собранному
  из документов других вузов. Если вуз не включил какую-то олимпиаду в свой перечень или
  профиль назван иначе, строка может отсутствовать или быть лишней — поэтому такие строки
  помечены бейджем «по профилю» и всегда снабжены ссылкой на источник.
* Уровень пары «олимпиада + профиль» определяется по большинству упоминаний в подробных листах
  (498 пар); для пар без уровня фильтр по уровню в правиле не применяется.
* Олимпиады **ДАНО** нет в исходной таблице (её нет в перечне РСОШ), поиск по ней вернёт пусто.
* 477 правил сформулированы без названий олимпиад и без профилей («весь перечень уровня I»,
  условия грантового конкурса) — разложить их в таблицу нечем, они показываются в блоке
  примечаний; часть направлений описана только такими правилами и таблиц не имеет.
* **Филиалы НИЯУ МИФИ** в источнике идут одной строкой «Филиалы», без разбивки по городам,
  поэтому в колонке города стоит «филиалы в регионах» и примечание об этом.
* У 11 848 связей (из 59 098) профиль не указан: это правила вузов, сформулированные общим
  текстом, и листы без колонки профиля (УрФУ, ВсОШ по предметам). В выдаче они попадают
  в «Все профили».
* Данные справочные: в каждой карточке есть ссылка на документ приёмной комиссии.
